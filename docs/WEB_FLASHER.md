# WolffBot Web Flasher

A fully static web page that writes the pre-built WolffBot firmware to an
ESP32-S3 over the Web Serial API. No backend, no database, no server-side
component — the page and the `.bin` files are the whole thing.

User-facing instructions are in [FLASHING.md](FLASHING.md). This document
covers how it works and how to deploy it.

---

## What it does — and does not do

**It does:**

1. Check that the browser exposes `navigator.serial`; if not, it says so and
   stops.
2. Load `firmware/manifest.json` and verify each `.bin` against the size and MD5
   recorded there before anything is written.
3. Ask the browser for a serial port (`navigator.serial.requestPort()`).
4. Connect, sync, and detect the chip: name, revision, MAC address and flash
   size, all via esptool-js.
5. Refuse to flash a non-ESP32-S3 chip unless the user explicitly ticks a
   confirmation box.
6. Write the four pre-built images at their recorded offsets, showing progress.
7. Verify each written image by comparing its MD5 against the flash contents.
8. Reset the board and report success or a human-readable error.

**It does not:**

- compile firmware;
- modify firmware (flash mode, frequency and size are passed as `keep`, so the
  values already in the built bootloader image are preserved);
- upload anything anywhere — nothing leaves the browser;
- require Arduino IDE, Python, ESP-IDF, PlatformIO, Node.js or a terminal from
  the person flashing.

## Stack

| Piece | Choice | Why |
| --- | --- | --- |
| Flashing | [`esptool-js`](https://github.com/espressif/esptool-js) 0.6.1 | Espressif's own browser port of esptool |
| Transport | Web Serial API | the only browser API that can talk to a serial bootloader |
| Verification | `js-md5` 0.9.2 | supplies `calculateMD5Hash` so esptool-js performs a real post-write MD5 check |
| Bundler | Vite 8 | static output, `base: "./"` so it works from any sub-path |
| UI | hand-written HTML/CSS, no framework | one page, nothing to gain from a framework |

## `manifest.json`

Generated by `tools/make_manifest.py` during `tools/build.sh`. The flasher reads
offsets and hashes from it rather than hard-coding them, so a rebuild
automatically updates what the page writes.

```json
{
  "name": "WolffBot",
  "version": "1.0.0",
  "chip": "ESP32-S3",
  "board": "Seeed Studio XIAO ESP32S3 (esp32:esp32:XIAO_ESP32S3)",
  "flash": { "size": "8MB", "mode": "dio", "freq": "80m", "partitionScheme": "default_8MB" },
  "parts": [
    { "offset": "0x0",     "path": "firmware/WolffBot-bootloader.bin", "size": 19984,  "md5": "…" },
    { "offset": "0x8000",  "path": "firmware/WolffBot-partitions.bin", "size": 3072,   "md5": "…" },
    { "offset": "0xe000",  "path": "firmware/boot_app0.bin",           "size": 8192,   "md5": "…" },
    { "offset": "0x10000", "path": "firmware/WolffBot-app.bin",        "size": 408864, "md5": "…" }
  ],
  "factory": { "offset": "0x0", "path": "firmware/WolffBot-factory.bin", "size": 474400, "md5": "…" }
}
```

## Chip detection

`ESPLoader.main()` connects, syncs and identifies the chip. The page then reads:

- `loader.chip.CHIP_NAME` — must start with `ESP32-S3`;
- the description returned by `main()` (includes package and revision);
- `loader.chip.readMac(loader)`;
- `loader.detectFlashSize()`.

MAC and flash size are informational — a failure to read them never blocks
flashing. The chip name is the gate: anything other than ESP32-S3 shows a
warning card and requires an explicit checkbox before the flash button will do
anything.

If the detected flash is smaller than the highest write offset, the flasher
raises the "not enough space" error instead of starting.

## Erase behaviour

Full-chip erase is **off** by default, matching the Arduino IDE
(`EraseFlash = Disabled`). esptool erases the sectors it writes, so the four
regions are replaced and user data elsewhere (NVS, SPIFFS) survives. The
"Полностью стереть flash" checkbox opts into `eraseAll`.

## Error handling

`describeError()` in `src/main.js` maps failures to plain-language Russian
messages with an actionable hint:

| Condition | Detected via |
| --- | --- |
| user cancelled the port picker | `NotFoundError` from `requestPort()` |
| insecure context / permission denied | `SecurityError` |
| port busy | "already open" / "failed to open serial port" / "in use" |
| device unplugged | "device has been lost", plus a `navigator.serial` `disconnect` listener |
| not in bootloader | "failed to connect" / "no serial data received" / "wrong boot mode" |
| timeout | "timeout" / "timed out" — suggests dropping to 115200 |
| verify failed | "md5" in the message |
| not enough flash | own pre-check, and esptool-js "doesn't fit" |
| erase failed | "erase" |
| unknown chip | "unknown chip" / "chip magic" / "unsupported" |
| firmware assets missing or corrupt | manifest fetch failure or size/MD5 mismatch |
| browser without Web Serial | `"serial" in navigator` is false |

The bootloader hint links Seeed's own XIAO ESP32S3 documentation rather than
asserting an unverified button sequence.

Everything esptool-js logs is mirrored into the collapsible **Журнал** panel, so
an unmapped failure is still diagnosable.

## Building and testing

```bash
cd web-flasher
npm install
npm run build      # -> dist/
npm run preview    # http://localhost:4173
```

`npm run dev` starts Vite's dev server. Web Serial needs a secure context, which
`localhost` satisfies, so the flasher is fully usable in development.

Verified in this repository: `npm install` and `npm run build` complete with no
errors; the built page loads with no console errors, no failed requests, a
correctly parsed manifest, all four parts listed, and the cancelled-port error
path rendering its message. **Not verified: an actual write to a physical
ESP32-S3.** No board was attached.

## Deployment

The build output is static files. Any static host works.

### GitHub Pages

`.github/workflows/pages.yml` builds `web-flasher/` and publishes `dist/` on
every push to the default branch. Enable it once under
**Settings → Pages → Build and deployment → Source: GitHub Actions**.

The site then lives at `https://<user>.github.io/<repo>/`. `vite.config.js` sets
`base: "./"`, so the sub-path needs no extra configuration.

### Vercel / Netlify / any static host

- Root directory: `web-flasher`
- Build command: `npm run build`
- Output directory: `dist`

### Serving `dist/` yourself

Any static file server will do, but it must be **HTTPS or `localhost`** — Web
Serial refuses to run in an insecure context.

## Security and privacy

- No backend, no analytics, no telemetry, no cookies.
- Serial access requires an explicit user gesture and an explicit port choice
  every session; the browser grants nothing implicitly.
- Firmware is verified against `manifest.json` hashes before writing and against
  flash contents after writing.
